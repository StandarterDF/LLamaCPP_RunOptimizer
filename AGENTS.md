# Правила проекта GGUFLauncher (исследование запуска модели)

## Жёсткие ограничения
- **Готовые релизы llama.cpp скачивать можно — только в `downloads/` проекта и обязательно
  вариант под CUDA 12.4** (не под другие версии CUDA). Использовать и сравнивать с существующим
  билдом `<папка llama.cpp>\`; чужие папки не трогать.
- **Скачивать можно по явному разрешению пользователя и только в папку `downloads/` проекта** —
  и только то, что действительно нужно для задачи (модели, спекуляторы, релизы движка).
  Всё скачанное распаковывать и запускать тоже внутри проекта; ничего не устанавливать глобально.
- **В других папках ничего не создавать, не изменять и не удалять.**
  Билд llama.cpp и модели — только чтение/запуск; свои файлы — в `downloads/` и рабочей папке проекта.
- **Личные пути не публикуются.** Реальные пути живут только в `config.local.bat` и
  `bench\env.local.json` (оба в `.gitignore`). Во всех `.bat` использовать переменные
  `%LLAMA_SERVER%`, `%LLAMA_DIR%`, `%MODELS_DIR%`, `%PROJECT_DIR%`; в наборах тестов — плейсхолдеры
  `${LLAMA_SERVER}`, `${LLAMA_DIR}`, `${MODELS_DIR}`, `${PROJECT_DIR}`. Перед коммитом прогонять
  `python bench\sanitize.py` и проверять, что в индексе нет путей пользователя.
- Модели по умолчанию использовать существующие; новые — в `downloads/` (или в папке моделей по
  явному указанию пользователя).
- **Для каждой новой запущенной модели — свой `.bat` запуска** в `launch\<сборка>\`. Одна модель =
  один рабочий конфиг; сверху короткий комментарий: квант, контекст, спекуляция, сэмплинг и итог
  по русскому. Пути — только через `%MODELS_DIR%`/`%LLAMA_DIR%`/`%PROJECT_DIR%`.
- **`.bat` — только с переводами строк CRLF.** Инструменты, пишущие LF (`write` и т.п.), ломают `cmd`:
  строки с `^` и `set` рассыпаются в «'…' is not recognized as an internal or external command».
  После создания любого `.bat` нормализовать переводы строк в CRLF (UTF-8 без BOM) и проверять запуском.
  PowerShell-фикс: прочитать файл, заменить LF на CRLF, записать `UTF8Encoding($false)`.
- Все результаты, логи, скрипты и выводы — только в этой папке.
- Документация и отчёты — на русском языке.
- Python-скрипты запускать интерпретатором из локального `.venv` (пакеты ставить только туда).

## Факты о среде
- GPU: NVIDIA GeForce RTX 4060 Ti 16 GB (sm_89, драйвер 616.92, CUDA UMD 13.4).
- CPU: AMD Ryzen 7 5700X (8C/16T), RAM 32 GB.
- Билд llama.cpp: `0.1.1-dev (build 10472, commit 60eeeb608)` — Windows x64, Clang 20.1.8, CUDA.
- Модель: Qwen3.5-архитектура (64 слоя, гибрид linear/full attention, GQA 24/4, MTP-голова), квант IQ2_S (~9.6 GB).
- Целевой режим: `llama-server`, один слот, длинный контекст (80k+), спекулятивное декодирование через MTP.
- Реальные пути задаются локально: `config.local.bat` (для `.bat`) и `bench\env.local.json` (для сценарцев
  `bench.py`). Образцы — `config.example.bat` и `bench\env.example.json`. Эти локальные файлы не коммитятся.

## План исследования
1. Базовая линия: конфиг пользователя и пример с карточки модели.
2. Перебор флагов: `-fa`, `-ctk/-ctv`, `-b/-ub`, загрузка (`--load-mode`), потоки, `--spec-*`.
3. Замеры: время загрузки, скорость prompt processing (PP), скорость генерации (TG), доля принятых draft-токенов, VRAM.
4. Итог: лучший .bat + инструкция + лог исследований по модели (например `docs\<модель>.md`).

**Методика замеров (обязательно):** скорость мерить только на реалистичных промптах —
`bench\requests_real.json` (RP/чат/код/математика/суммаризация). Повторяющийся «тест-заполнитель»
(`make_prompt`, ключ `target`) даёт ~100 % принятия спекуляции и завышает TG в 1.5–2 раза; он годится
только как стресс-тест и в итоговые таблицы не попадает. Готовые наборы — `bench\suites\real_*.json`.

**Перед новым исследованием** свериться с реестром `docs\researched.md` (что уже проверено и с каким
вердиктом) — чтобы не повторяться. Каждую новую проверку вносить туда (вердикт + ссылка).

## Документация: как писать README и логи

### README.md — витрина для человека, а не лог исследований
- Только итоговые результаты и рекомендации. Хронология, «почему запускался каждый тест»,
  черновики и перебранные варианты — в логи, не сюда.
- Обязательные разделы:
  1) что это за репозиторий и стенд (1–3 строки);
  2) быстрый старт (2–4 шага);
  3) таблица готовых конфигов: *модель → задача → итоговая скорость → файл конфига*;
  4) рекомендованные модели по задачам (RP/креатив, код/агенты, чат, русский язык, длинный контекст);
  5) рекомендации по железу — отдельно для разных видеокарт (VRAM), с пометкой, что измерено, а что ориентир;
  6) рекомендации по задачам — кодинг/агенты, RP/креатив, длинные документы, мультипользовательский режим;
  7) короткие правила, которые дают больше всего;
  8) «чего избегать» (проверенные анти-паттерны);
  9) ссылки на подробности; 10) воспроизведение замеров.
- **В раздел «Рекомендованные модели» попадают ТОЛЬКО модели, которые реально запускались и
  измерялись в этом репозитории** (есть лог в `docs\` и/или прогон в `bench\runs\`). Непроверенные
  кандидаты сюда не добавлять — им место в логах/внешнем ресёрче с пометкой «не проверено».
  Для каждой — задача и один короткий довод (по замерам), без простыней.
- Конфиги не дублировать текстом — **ссылаться на рабочие файлы** (`launch\...\*.bat`).
  В README писать, что выбрать и почему, а не готовую команду.
- Числа — только итоговые (t/s, ГБ) с единицами измерения; простыни таблиц оставлять в логах.
- Советы делать адресными: «если у вас 8/12/16/24 ГБ», «для кодинга», «для RP» — а не «в общем случае».
- Обновил конфиг — обнови таблицу в README.

### Логи исследований — отдельный файл на модель в `docs\`
- Имя: `docs\<модель>.md` (нижний регистр, дефисы). В начале: модель/квант, драфт, стенд,
  методика в 1–2 строки со ссылкой на `bench\`.
- Обязательно: таблицы всех серий (тест → что проверяли → метрики → вывод), краткое «зачем каждый тест»,
  итоговый конфиг со ссылкой на `.bat`, раздел «не проверено».
- Кросс-модельные темы (методы спекуляции, сравнение сборок, форки) — отдельный `docs\<тема>.md`.
- Лог — это журнал: даты, «опровергнуто», аномалии загрузки и предупреждения сервера здесь уместны.

### Общие правила текстов
- Русский язык; флаги, пути, команды — как есть; технические термины можно оставлять английскими.
- Каждое утверждение о скорости подкреплять ссылкой на источник: `bench\runs\results.jsonl` или лог модели.
- **Оценки качества RP/прозы не выставлять без согласования с пользователем.** Харнесс меряет
  скорость и языковые артефакты, но **не** качество ролеплея. «Быстро генерирует на RP-промптах» ≠
  «хороша в RP»: не ставить модели в рейтинг RP по скорости или проценту принятия спекуляции.
  Любые RP-предпочтения (какая модель лучше «в роли», в прозе, в креативе) — только после
  согласования с пользователем.
- Честно помечать непроверенное и экстраполяции («12/8/24 ГБ не измерялись — ориентиры»).
- Не дублировать факты: один факт живёт в одном месте, остальные ссылаются на него.
- При переносе/переименовании файлов сразу править все перекрёстные ссылки, а после — проверять,
  что пути в таблицах реально существуют (smoke-check).
- Корень держать чистым: `README.md` + `AGENTS.md`; конфиги — `launch\`, логи — `docs\`,
  инструменты — `bench\`, скилы — `.opencode\skills\`.
