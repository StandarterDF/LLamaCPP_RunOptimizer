# Память контекста: эмпирическая модель (VRAM → максимальный ctx)

**Что это.** Формула и инструмент, чтобы по весу модели, типу KV и объёму VRAM заранее
(без запуска) оценить, **сколько контекста поместится** и сколько памяти уйдёт. Калибровка — по
фактическим замерам из `bench\runs\**\results.jsonl` (там пишут `vram_before_mb` /
`vram_after_load_mb`, `-c` и тип KV).

**Инструмент:** `bench\vram_model.py` (только stdlib + `bench\gguf_info.py`).

```powershell
# калибровка + отчёт по всем логам
.\.venv\Scripts\python.exe bench\vram_model.py --fit
# предсказание для конкретного GGUF (GPU по умолчанию 16380 МиБ = 16 ГБ)
.\.venv\Scripts\python.exe bench\vram_model.py --model <path.gguf> --tk q4_0 --tv q4_0 --reserve 700
```

## 1. Формула

```
VRAM_after_load = VRAM_before + W + KV_arch(ctx, tk, tv) + O

ctx_max  =  максимальный ctx, при котором   W + KV_arch(ctx) + O  ≤  GPU − reserve − VRAM_before
```

| Слагаемое | Как считается |
| --- | --- |
| `W` | размер файла GGUF (МиБ) — ровно |
| `KV_arch(ctx)` | **точно по архитектуре из GGUF** (`gguf_info`): полные слои — весь ctx; SWA-слои — `min(ctx, окно)`; гибридные Qwen — только слои attention; K и V считаются раздельно по своему типу |
| `O` | накладные (compute-граф, CUDA-контекст, активации батча) — **эмпирически**, зависит от типа модели, а не от веса |
| `VRAM_before` | рабочий стол до загрузки (~0.6–1.1 ГиБ); по умолчанию 700 МиБ |
| `reserve` | запас, чтобы не поймать OOM/свит (по умолчанию 700 МиБ) |

`KV_arch` — единственная «архитектурная» часть; она точная (не эмпирическая), поэтому формула
корректно переносится между семействами.

## 2. KV на токен по архитектурам (КиБ, ctx больше окна; из GGUF)

| Модель | Архитектура | Attn-слоёв | f16 | q8_0 | q4_0 |
| --- | --- | --: | --: | --: | --: |
| Gemma-4-26B-A4B (MoE) | gemma4, SWA окно 1024 | 5 | 20.0 | 10.6 | 5.6 |
| Gemma-4-31B / Dark-Thoughts V2 | gemma4, SWA окно 1024 | 10 | 80.0 | 42.5 | 22.5 |
| Qwen3.8-27B (Swift, dense) | qwen35, гибрид 1/4 | 16 | 64.0 | 34.0 | 18.0 |
| Qwen3.6-27B Fable (dense) | qwen35, гибрид 1/4 | 16 | 64.0 | 34.0 | 18.0 |
| Qwen3.6-35B-A3B (MoE) | qwen35 (раскладка не в GGUF) | ~16 (оценка) | ~64 | ~34 | ~18 |

Как читать: у Gemma-4 «лишние» слои — SWA (окно 1024), поэтому вклад в контекст дают только
**полные** слои (5 у 26B-A4B, 10 у 31B). У Qwen3.5/3.6 KV держит каждый 4-й слой (DeltaNet-слои
состояния не накапливают). Отсюда, например, 27B Qwen (18 КиБ/токен q4_0) экономичнее плотной
Gemma-31B (22.5 КиБ/токен), несмотря на близкий размер.

## 3. Накладные O (эмпирика)

Калибровка по чистым замерам (`--fit`; из выборки исключены прогоны со спекуляцией, mmproj и
выгрузкой экспертов):

| Тип | N | Медиана O | Разброс |
| --- | --: | --: | --- |
| **dense** (31B, 27B) | 14 | **~640 МиБ** | 51…854 |
| **MoE** (26B-A4B, 35B-A3B) | 13 | **~0** (десятки МиБ) | −2249…96 |

Вывод: `O` почти не зависит от веса, но **резко падает у MoE** — compute-граф считает только
активных экспертов. В инструменте взяты консервативные дефолты `--o-dense 750`, `--o-moe 200`
(запас на батч/пики). Спекуляция/MTP добавляет ещё свой draft-контекст — в калибровке не учтён
(на RP всё равно не используется, см. `docs\quality\rp-quality-eval.md` §5.18).

## 4. Примеры (16 ГБ, KV q4_0, reserve 700, VRAM_before 700)

| Модель | W, МиБ | KV/ток | **ctx_max** | Проверка |
| --- | --: | --: | --: | --- |
| Qwen3.6-27B Fable **i1-IQ3_S** | 12 019 | 18 КиБ | **~125 000** | замер при 51200: 13 856 МиБ (модель 13 633) ✓ |
| Schattenblume-31B i1-IQ3_XXS (dense) | 11 518 | 22.5 КиБ | **~113 000** | известно из проекта: q4_0 даёт ~116k ✓ |
| StyleTune-26B-A4B IQ4_XS (MoE) | 13 786 | 5.6 КиБ | **~170 000** | — |
| Schattenblume-31B при KV f16 | 11 518 | 80 КиБ | ~35 000 | известно: f16 держит лишь ~26k порядок ✓ |

Практика: **KV q4_0 в 3.6× экономичнее f16** → именно он даёт длинный контекст на 16 ГБ.
Тип KV на качество почти не влияет (NIAH/память/PPL, `docs\research\kv-cache-quantization.md`).

## 5. Ограничения и грабли

- **Гибридные Qwen (3.5/3.6/3.8).** GGUF часто **не отдаёт** `attention.layer_types`, поэтому
  инструмент применяет правило «attention — каждый 4-й слой». Для 27B это верно (16/65);
  для 35B-A3B оценка грубее — сверяйте с реальной загрузкой (`--fit`, группы с отрицательным O).
- **`--fit on` при переполнении сам скидывает слои на CPU** → VRAM ниже, скорость падает. Поэтому
  `ctx` держать в пределах предсказания; `--fit-target` влияет на запас.
- **Спекуляция (MTP/DFlash)** — отдельный draft-контекст, в O не входит.
- **mmproj (vision)** и `--n-cpu-moe` искажают замер → исключены из калибровки.
- **`VRAM_before` плавает** (0.6–1.1 ГиБ от рабочего стола/браузера) — это главный разброс;
  меняйте `--reserve`/`--before`.
- Числа — под **одну сессию** (n_slots=1, `--models-max 1`). Многослотность делит контекст.

## 6. Как перемерить/расширить калибровку

Логи уже содержат всё нужное. Достаточно прогнать сервер с `--log-file` (harness `bench\bench.py`
пишет `vram_before_mb`/`vram_after_load_mb` в `bench\runs\<test>\results.jsonl`), добавить модели —
и повторить `--fit`. Формула сама подтянет новые архитектуры, если GGUF отдаёт корректные
`block_count`, `head_count_kv`, `key_length`, `sliding_window_pattern`/`layer_types`.

См. также: `bench\gguf_info.py` (метаданные + KV), `docs\research\kv-cache-quantization.md`,
`docs\quality\rp-quality-eval.md` §5.18 (RP-скорость и MTP).
