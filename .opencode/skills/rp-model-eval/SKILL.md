# RP Model Eval

Скил превращает «протестируй модель на RP» в один воспроизводимый запуск: генерация → судья →
средние баллы. Он не заменяет [bench\rp_quality.py](../../../bench/rp_quality.py), а оборачивает его и убирает ручное чтение
харнесса каждый раз.

## Жёсткое правило объёма (экономия)

1. **Скрин — базовый набор (2 сценария, `scenarios_rp.json`): school + seduction.** Гоняется для
   ЛЮБОЙ новой модели, оба режима (`nothink`, `think`), 3 сида.
2. **Полный набор (6 сценариев, `scenarios_rp_full.json`) — только для моделей, которые на скрине
   показали себя лучше всех** (примерно верхняя половина таблицы или явный лидер по нужной оси).
   Не гонять полный набор «на всякий случай»: это 36 генераций + судейство на модель.
3. Скорость (t/s) и «Чисто %» — побочные метрики; они не заменяют оценку судьи.

## Когда использовать

- «Протестируй/оцени модель X на RP», «на что способна модель в роли».
- «Сравни модели по RP», «поставь базовую модель против файнтюна».
- Нужны баллы по 8 осям (ум, память, персонаж, инструкция, инициатива, русский, проза, повторы).

Не для этого скила: чистая скорость/конфиг запуска (это `LLM Launch Tuner`), русский без RP
([docs\quality\sampling-quality.md](../../../docs/quality/sampling-quality.md)), подбор кандидатов на HF (`gemma4-ru-rp-researcher`).

## Быстрый старт (одна команда)

> **Путь модели — в ОДИНАРНЫХ кавычках.** В PowerShell `${MODELS_DIR}` в двойных кавычках
> раскроется как пустая переменная и путь сломается. Одинарные кавычки не раскрываются.

```powershell
# базовый скрин: 2 сценария × nothink/think, ПАНЕЛЬ 4 СУДЕЙ (по умолчанию)
.\.venv\Scripts\python.exe .opencode\skills\rp-model-eval\scripts\run_eval.py `
  --name base_gemma26 `
  --model '${MODELS_DIR}/unsloth/gemma-4-26B-A4B-it-GGUF/gemma-4-26B-A4B-it-UD-IQ3_XXS.gguf' `
  --family gemma --scenarios base --modes nothink,think --judges gemma,qwen,dsflash,dsv4pro
```

`--judges` можно не указывать: **по умолчанию — 4 судьи** (`gemma,qwen,dsflash,dsv4pro`).
Облачным (`dsflash`, `dsv4pro`) нужен ключ `DEEPSEEK_API_KEY` в `.env`; без него скрипт
останавливается с ошибкой, чтобы не выдать молча оценку по 2 судьям вместо 4. Оффлайн/быстро:
`--judges gemma,qwen` (только локальные, GPU).

Что произойдёт: создаст `bench\quality\suites\suite_rp_eval_<name>_{nothink,think}.json`, поднимет/погасит
`llama-server` на каждый режим (по одному), запишет прогоны в `bench\quality\runs\rp_eval_<name>_<mode>\`,
затем судит все прогоны **четырьмя судьями** — по очереди два локальных (`rp_judge.py`) и два облачных
(`api_judge.py`, параллельно) — и посчитает средние баллы по каждому судье и **единое «среднее по 4 судьям»**
(`judge_score.py`).

> **Один сервер на оба режима — `--single-server`** (экономит одну загрузку модели на прогон,
> особенно заметно на моделях 20+ ГБ). Сервер поднимается в think-конфиге, а nothink получается
> **per-request** `chat_template_kwargs {"enable_thinking": false}` (через `/apply-template`).
> Проверено на gemma-4: ответы `raw` и `raw_full` **байт-в-байт идентичны** обычному
> двухсерверному пути, и в nothink, и в think. Для не-gemma семейств сначала проверьте, что шаблон
> уважает `enable_thinking`; при сомнении не используйте флаг (по умолчанию — старый путь).
> Флаг влияет только на фазу генерации; имена каталогов прогонов не меняются, поэтому судейство и
> реестры сравнимы.

Полный набор для лидера:

```powershell
... run_eval.py --name base_gemma26_full --model '<тот же gguf>' `
  --family gemma --scenarios full --modes nothink,think --judges gemma,qwen,dsflash,dsv4pro
```

Только судейство по уже готовым прогонам (генерация пропускается):

```powershell
# все 4 судьи (досчитать облачных к уже готовым локальным — обычный случай)
... run_eval.py --name <name> --model '<gguf>' --skip-generate --judges gemma,qwen,dsflash,dsv4pro
# только локальные
... run_eval.py --name <name> --model '<gguf>' --skip-generate --judges gemma,qwen
```

## Логи прогона (смотреть ход исследований)

Каждый запуск пишет **единый лог** `logs\rp_eval_<name>_<stamp>.log`: фазы, полный поток вывода
харнесса (по каждой генерации), вывод судей и сводку баллов. Путь печатается в начале и в конце.
Свой путь — флагом `--log <файл>`.

Чтобы следить за прогоном в реальном времени:

```powershell
Get-Content logs\rp_eval_<name>_<stamp>.log -Wait -Tail 40
```

Рядом лежат технические логи: `bench\quality\runs\rp_eval_<name>_<mode>\server.log` (сервер модели)
и `bench\quality\runs\rp_judge_<judge>_<name>\run.log` (сервер судьи).

## Параметры `run_eval.py`

| Флаг | Смысл |
| --- | --- |
| `--name` | короткое имя прогона; попадает в имена suite/каталогов |
| `--model` | путь к GGUF; поддерживает `${MODELS_DIR}` и др. плейсхолдеры |
| `--family` | `gemma` (внешний `gemma4.jinja`, без MTP) · `qwen` (встроенный шаблон + `draft-mtp`) · `other` |
| `--modes` | `nothink,think` (по умолчанию оба) |
| `--scenarios` | `base` (2 сценария, скрин) · `full` (6, только для лидеров) |
| `--seeds` | по умолчанию `11,22,33` |
| `--judges` | панель судей. По умолчанию **`gemma,qwen,dsflash,dsv4pro`** (4 судьи). Только локальные — `gemma,qwen`; отключить — `none`. `dspro` — синоним `dsv4pro` |
| `--judge-batch` | ответов на один запрос судьи (по умолчанию 3) |
| `--judge-concurrency` | параллельных запросов **облачных** судей (`api_judge.py`), по умолчанию 10 |
| `--draft` | внешний MTP-драфт (`-md`); иначе встроенная MTP-голова модели |
| `--no-spec` | выключить спекуляцию |
| `--single-server` | один `llama-server` на оба режима (одна загрузка модели); nothink — per-request `enable_thinking=false`. Проверено на gemma (ответы идентичны). Экономит загрузку; судейство/каталоги не меняются |
| `--single-server-port` | порт сервера для `--single-server` (по умолчанию 9953; не совпадать с 9931/9932/9952) |
| `--ctx`, `--threads` | 51200, 12 по умолчанию (как в RP-конфигах проекта) |
| `--reasoning-budget-think` | бюджет мышления в think (по умолчанию 1024; `-1` — безлимит) |
| `--reuse` | не перегонять режим, если `metrics.jsonl` уже есть |
| `--skip-generate` / `--skip-judge` | пропустить соответствующую фазу |
| `--log` | путь к единому логу прогона (по умолчанию `logs\rp_eval_<name>_<stamp>.log`) |

Сэмплинг фиксирован: **RU-safe temp 0.6 / min-p 0.1 / top-k 0 / top-p 0.95** — чтобы баллы были
сравнимы с уже прогнанными моделями ([docs\models.md](../../../docs/models.md), [docs\quality\rp-quality-eval.md](../../../docs/quality/rp-quality-eval.md)).

## Судьи: панель из 4 (и их ограничения)

Штатная оценка — **четыре судьи** (та же панель, что в витрине [docs\quality\rp-ranking.md](../../../docs/quality/rp-ranking.md)):

| Судья | Где | Модель / канал | Характер шкалы |
| --- | --- | --- | --- |
| `gemma` | локально (`rp_judge.py`) | `gemma-4-26B-A4B-it-UD-IQ3_XXS`, `gemma4.jinja` | мягче, ~4.4 |
| `qwen` | локально (`rp_judge.py`) | `Qwen3.6-35B-A3B-MXFP4_MOE` (влезает за счёт MoE + `--fit on`), `--spec` | строже, ~3.3 |
| `dsflash` | облако (`api_judge.py`) | `deepseek-flash`, `thinking=disabled` | независимый, вне GPU |
| `dsv4pro` | облако (`api_judge.py`) | `deepseek-v4-pro`, `thinking=disabled` | независимый, вне GPU |

- **Баллы сравнивать только внутри одного судьи** — у всех разные шкалы (26B мягче, Qwen строже,
  облачные — свой уровень). «Среднее по 4 судьям» — это **единая цифра панели**; с ней модель
  сопоставима со строками [docs\quality\rp-ranking.md](../../../docs/quality/rp-ranking.md).
- **Ключ:** облачным судьям нужен `DEEPSEEK_API_KEY` в `.env` (gitignored, шаблон `.env.example`).
  Нет ключа → `run_eval.py` падает с понятной ошибкой (не выдаёт 2 судьи за 4).
- **Самооценка.** Если оцениваемая модель — gemma-26B, Qwen3.6 или DeepSeek, соответствующий судья
  судит сам себя. Пометку об этом писать в отчёт: у DeepSeek это касается строк V4-Pro / V4.1-Flash.
- Облачные судьи дают независимый голос, но **не отменяют локальных**: по опыту витрины они строже
  к локальным мержам (напр. heretic-ARA: локально 4.44/3.52, в панели 3.59).
- API-прогоны судей не пишут `run.log` сервера (сервера нет) — их вывод только в едином логе прогона.

## Что читать после прогона

1. **Лог прогона** `logs\rp_eval_<name>_<stamp>.log` — ход всего исследования (фазы, поток харнесса, судьи).
2. Сводку `judge_score.py` (печатает `run_eval.py` в конце и пишет в лог) — средние по 8 осям
   **по каждому судье** и **единое «среднее по 4 судьям»** (последняя сводка, объединяющая все каталоги судей).
3. Тексты судьи — `bench\quality\runs\rp_judge_<judge>_<name>\*.txt` (искать конкретные проблемы);
   `<judge>` = `gemma`, `qwen`, `dsflash`, `dsv4pro`.
4. Сырые ответы — `bench\quality\runs\rp_eval_<name>_<mode>\raw\`; с thinking — `raw_full\`.
5. Объективные метрики — `bench\quality\runs\rp_eval_<name>_<mode>\summary.md`.

Порядок анализа: сначала заключение судьи (обычный текст), и только при сомнительных местах —
сырой транскрипт. Судья-26B иногда переусердствует и наговаривает (проверять по `raw\`).

## Известные грабли (проверено)

- **Think часто сломан**: незакрытый `<channel|>`/` thinking` → пустой ответ. `strip_channels` в
  [bench\rp_quality.py](../../../bench/rp_quality.py) срезает и gemma-канал, и ` thinking`; но если модель вообще не закрывает канал
  за `n_predict`, ответ теряется. В отчёте честно писать «think непригоден в llama.cpp».
- **Самооценка** (см. выше) — не выдавать за независимый вердикт.
- **Облачные судьи (DeepSeek).** Без `DEEPSEEK_API_KEY` в `.env` скрипт падает на предпроверке (так и
  задумано — не подменять панель из 4 судей двумя). Облачный судья не занимает GPU, поэтому локальные
  и облачные судьи можно считать не по очереди, но `run_eval.py` сейчас гоняет их последовательно.
  Для строк DeepSeek-моделей `dsflash`/`dsv4pro` — self-eval (помечать).
- **Судья-26B пропускает пункты** → N меньше числа ответов; гонять батчами по 3.
- **Спекуляция на RP** у dense/MoE-моделей может не окупаться (см. `gemma4-26a4b-styletune-nothink-nospec`).
  Скорость здесь не цель.
- **Один сервер за раз**: генерация и судья поднимают `llama-server` на GPU. Не запускать параллельно.
- **VRAM судьи**: `rp_judge.py` сам проверяет свободную VRAM (`--min-free-mb`, 12000) и падает,
  если занято. Освободить GPU перед запуском.
- **`.bat` — только CRLF.** Если создаёшь конфиги запуска — нормализовать переводы строк.

## После прогона: обновить документацию (обязательно, не откладывать)

> **Правило (подтверждено пользователем):** после каждого теста держать все `.md` актуальными.
> Рейтинг-таблицы обновляются **автоматически по замерам** — отдельного согласования они не требуют;
> согласовывать нужно только субъективные «вкусовые» предпочтения (что лучше лично вам).

1. [docs\researched.md](../../../docs/researched.md) — строка в разделе «Качество RP (LLM-судья)»: что проверяли, вердикт, ссылка.
2. [docs\models.md](../../../docs/models.md) — строка в «Протестированные» (или «Кандидаты»); для базовых/не-RP моделей —
   пометка, что RP мерили.
3. Лог/раздел с числами — [docs\quality\rp-quality-eval.md](../../../docs/quality/rp-quality-eval.md) (новый подраздел) или отдельный `docs\<модель>.md`.
4. **[docs\quality\rp-ranking.md](../../../docs/quality/rp-ranking.md) — вставить строку в таблицы Non-Think / Think** со средним по 4 судьям
   (колонки: `#`, модель, Type, RP, `сц`, примечание), **пересчитать нумерацию** ниже, поправить строку
   в «Быстрый вывод» и оговорки (self-eval/родственная база). Число берётся из итоговой сводки
   `judge_score.py` по всем четырём каталогам судей.
5. Для новой запущенной модели — `.bat` в [launch\b11382-cu124](../../../launch/b11382-cu124) (think и nothink, если умеет оба).
6. Прогнать [bench\check_links.py](../../../bench/check_links.py) и [bench\check_bats.py](../../../bench/check_bats.py); при переносе файлов — сразу править ссылки.

См. `references/pipeline.md` — полная методика, устройство харнесса и формат suite.
