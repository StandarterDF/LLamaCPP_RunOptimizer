# Методика подбора конфига запуска LLM

Дополняет `SKILL.md`: подробности фаз, дизайн экспериментов, метрики, артефакты.

## 0. Что считаем «лучшим конфигом»

Порядок приоритетов:
1. **Качество и корректность** (ответы, шаблон, мышление) — не жертвовать без согласования.
2. **Скорость генерации (TG) на реальных задачах** — главный критерий.
3. **Задержка/PP** (время до первого токена, длинные промпты).
4. **Запас VRAM** и стабильность (не «в притык»).
5. Простота конфига.

«Лучший по тесту-заполнителю» ≠ «лучший на реальной работе»: повторяющийся текст даёт ~100 % принятия
спекуляции и завышает TG в 1.5–2 раза. Поэтому обязательны реалистичные задачи, минимум:
**RP/креатив** (высокая энтропия — главный источник расхождений), чат, код, математика/рассуждение.
Не используйте повторяющийся `target`-заполнитель как основной замер — только как стресс-тест.

## 1. Дизайн экспериментов

- **Один фактор за раз.** Меняем один флаг, остальное фиксировано.
- **Повторы.** Один конфиг даёт разброс ±5 %; отличающиеся меньше — считать равными
  (выбирать по простоте, запасу VRAM, меньшему числу флагов).
- **Реалистичные запросы.** Фиксированные seed/промпты у всех тестов; `cache_prompt: false` в замерах,
  чтобы мерить честный PP (кэш проверяется отдельным сценарием).
- **Глубина.** Мерить PP/TG не только на коротком, но и на ~12k и (для агентных задач) 32–60k.
- **Состояние машины.** Фиксировать, что ещё ест GPU/VRAM (браузер, рабочий стол); не мерить в игре.
- **Чистота.** Сервер убивать после каждого теста, порт не занимать, в чужих папках ничего не менять.
- **Личные пути не публикуются.** Реальные пути держите в `env.local.json` (в `.gitignore`), а в наборах
  тестов используйте плейсхолдеры `${LLAMA_SERVER}`, `${LLAMA_DIR}`, `${MODELS_DIR}`, `${PROJECT_DIR}` —
  `bench.py` раскрывает их из `env.local.json` и сам санитизирует аргументы и логи. Перед публикацией
  запускайте `scripts/sanitize.py` и проверяйте, что в файлах нет путей пользователя.

## 2. Фаза 0: инвентаризация

1. Железо: `scripts/probe_env.py` (GPU, VRAM, драйвер, CPU, RAM, версия llama-server).
2. Модель: размер файла, суффикс `-mtp` (спекулятивная голова), мультимодальность (`mmproj`),
   число слоёв/архитектура (смотрится при загрузке в логе сервера).
3. Требования: целевой контекст, число одновременных клиентов (`-np` делит контекст), агентность
   (tools), допустимость квантования KV.
4. Карточка модели: рекомендованный сэмплинг (temp/top-p/top-k/min-p/штрафы), нюансы шаблона,
   предупреждения (например «vision-проектор не валидирован»), KLD по квантам.
5. Зафиксировать текущий способ запуска пользователя (он — кандидат baseline).

## 3. Фаза 1: baseline

- Скопировать `scripts/` в рабочую папку проекта (обычно [bench](../../../../bench)).
- Собрать suite на основе `assets/suite-template.json`: 2 теста (текущий конфиг + дефолтный с FA/fit).
- `python bench/bench.py suite.json` → `runs/results.jsonl`, логи, ответы.
- Зафиксировать: загрузка, VRAM, PP 1.5k, PP 12k, TG 1.5k, TG на 2–3 чатах, принятие спекуляции.
- Посмотреть в логи: реальный `n_ctx`, ошибки (например «quantized V cache requires flash_attn»),
  строки `slot print_timing` (PP/TG/принятие по каждому запросу).

## 3.5. Бюджет времени: быстрый режим (по умолчанию)

Полный перебор «в лоб» легко съедает 40+ минут на модель. Рабочий быстрый цикл:

1. **1 baseline-тест** (текущий конфиг) — без изменений.
2. **4–6 тестов на модель**, по одному фактору: сначала спекуляция (`n-max`, `p-min`), затем контекст,
   затем KV/загрузка. Батчи и потоки не проверять — заведомо шум.
3. **Минимальный набор запросов**: 2 реальные задачи по 256–320 токенов + один PP-замер (~8k токенов)
   **один раз на модель**. Не мерить PP на глубине для каждой конфигурации.
4. Промпты/сэмплинг, меняющиеся на стороне запроса, проверять на одном запущенном сервере — без перезапусков.
5. Один тест ≈ 1–2 минуты; серия на модель — **10–15 минут**. Ориентир для suite:
   `short: target 1000, n_predict 128`, `long: target 8000, n_predict 32`, 2 чата по 256–384 токена.
6. Финальную пару конфигов прогнать повторно, чтобы отсеять разницу меньше ±5 %.

Ориентировочный шаблон: `assets/suite-template.json`. Полная версия (3 задачи, 12k-промпт) нужна
только для финальной валидации победителя.

## 4. Фаза 2: тюнинг

Порядок и типичный выигрыш:

| Шаг | Что меняем | Ожидаемый эффект |
| --- | --- | --- |
| 1 | Включить спекуляцию (`draft-mtp` / `draft-simple` / ngram) | +20…+100 % TG |
| 2 | `--spec-draft-n-max` 2…6, `--spec-draft-p-min` 0.0…0.7 | ещё ±10 % |
| 3 | KV: q4_0 / q8_0 / f16 | VRAM (→ контекст), редко скорость |
| 4 | Контекст: сколько влезает с запасом 1.5–2 ГБ | функциональность; следить за TG на глубине |
| 5 | `--fit on/off`, `-ngl`, `--load-mode` | память/время загрузки |
| 6 | `-b/-ub`, `-t/-tb` | обычно шум; не тратить время |
| 7 | Отдельные профили: длинный контекст, агентный (ngram) | для конкретных сценариев |

Правила интерпретации:
- Смотреть **итоговый TG**, а не процент принятия. Высокое принятие при малом числе драфтов =
  меньше токенов за шаг. (У нас `p-min` 0.9 → принятие 92 %, но TG ниже, чем при 0.5.)
- Если спекуляция «не даёт» прироста: проверить, что модель с головой (`-mtp`), тип спекуляции
  поддерживается билдом (`--spec-type ...` есть в `--help`), и что сервер не ушёл на CPU.
- Если большой контекст резко роняет TG — уменьшить драфты (`n-max 3, p-min 0.7`) или контекст.

## 5. Фаза 3: мультитёрн, кэш, качество

### Кэш промпта
Сценарий: длинный системный префикс (~5–8k токенов), затем 2–3 хода с возвратом истории.
- С `cache_prompt: true` 2-й запрос должен пересчитать десятки токенов (в `usage.prompt_tokens_details.cached_tokens`
  почти весь промпт), время — секунды вместо десятков секунд.
- `cache_prompt: false` — полный пересчёт, это «худший случай» для сравнения.
- `--cache-reuse` нужен только для частичных совпадений; для точного префикса не обязателен.

### Шаблон и мышление
- Проверить рендер: `curl`-ом отправить чат и посмотреть `content`/`reasoning_content`.
- Допустимые режимы мышления брать из шаблона модели, а не из общей справки сервера
  (например сервер принимает `minimal/high/max`, а шаблон — только `xhigh/medium/low`).
- Для агентов: `--reasoning-preserve` (если шаблон поддерживает), tools-вызовы.

### Качество ответов
2–3 эталонные задачи, ответы сохранять (`*-answer.txt`), проверять факт правильности руками.
Смена сэмплинга (temp и т.п.) — только по согласованию, это влияет на смысл результатов.

## 6. Фаза 4: артефакты

- `launch/*.bat` (или shell-эквивалент) — по шаблону `assets/launch-template.bat`.
- `LAUNCH.md` — итоговая инструкция: основной профиль, альтернативы, таблица ожидаемых метрик,
  «почему так», «чего избегать», ограничения (шаблон: `assets/launch-doc-template.md`).
- `FINDINGS.md` — журнал: каждая серия, таблица замеров, выводы (шаблон: `assets/findings-template.md`).
- `runs/summary.md` — генерируется `report.py`.
- Проверка результата: запустить финальный конфиг и прогнать короткий контрольный suite.

## 7. Типичные ошибки

- Мерить на одном заполняющем промпте и радоваться 2.4×, которых нет на реальных задачах.
- Выбирать конфиг по одному прогону без учёта разброса ±5 %.
- Забыть про квантованный V-кэш + `-fa off` (сервер не стартует) или про `-fa` вообще.
- Ставить контекст «на всю VRAM»: глубина и спекуляция просядут.
- Подключать чужие mmproj/draft-модели без валидации авторов.
- Оставлять работающий сервер после тестов (занимает VRAM/порт).
- Писать артефакты куда попало: всё должно лежать в рабочей папке проекта (и быть воспроизводимым).
