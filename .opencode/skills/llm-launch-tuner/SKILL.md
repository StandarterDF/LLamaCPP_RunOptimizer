# LLM Launch Tuner

Скил превращает «подбери оптимальный запуск модели» в воспроизводимый цикл:
инвентаризация → baseline → серии бенчмарков → отбор → готовый конфиг и документация.

Проверено на практике (Swift-1.5-Qwen3.8-27B IQ2_S-mtp, RTX 4060 Ti 16 GB, llama.cpp build 10472):
итоговая прибавка к генерации +75 % только за счёт спекуляции MTP и правильных флагов.

## Когда использовать

- «Подбери лучший конфиг/флаги запуска для модели X», «модель работает медленно».
- «Протестируй/сравни кванты, контекст, KV-кэш, батчи, спекуляцию».
- Нужен обоснованный `launch.bat`/команда и отчёт с числами.

## Жёсткие правила (по умолчанию)

1. **Ничего не скачивать** (модели, сборки, пакеты), пока пользователь явно не разрешил. Использовать, что есть.
2. **Не менять чужие файлы.** Билд/модель — только запуск. Все артефакты — в рабочую папку проекта.
3. **Один сервер за раз.** Бенчмарки занимают GPU; предупредить, если на машине идут игры/рендер.
4. **Не перезаписывать результаты** прошлых серий: каждому прогону — своя строка в `results.jsonl`.
5. **Кандидаты — по одному фактору за раз** и с повторной проверкой на 2–3 реальных задачах, а не на одном промпте.
6. Если пользователь просит не трогать папку llama.cpp/модель — работать только на чтение/запуск.

## Рабочий процесс

Полная методика: `references/methodology.md`. Специфика llama.cpp и анти-паттерны: `references/llama-cpp-playbook.md`.
Шаблоны: `assets/`.

### Фаза 0. Инвентаризация

1. Железо и софт: GPU/VRAM, драйвер, CPU, RAM, ОС; версия рантайма (`llama-server --version`).
   Быстрый снимок: `python scripts/probe_env.py --llama-server <путь>`.
2. Модель(и): файл GGUF, размер, MTP/EAGLE-голова (суффикс `-mtp`), мультимодальность.
3. Требования пользователя: нужный контекст, один/несколько клиентов, агентность (tools), язык/качество.
4. Карточка модели (HF/GitHub): рекомендованный сэмплинг, особенности шаблона (например допустимые
   `reasoning_effort`), предупреждения о vision-проекторе, KLD/перплексия по квантам. **Сверить с тем,
   как модель запускают сейчас** — расхождения фиксировать в отчёте.

### Фаза 1. Baseline

1. Скопировать `scripts/` скила в рабочую папку (например [bench](../../../bench)) — для воспроизводимости.
2. Собрать suite из `assets/suite-template.json`: текущий конфиг пользователя + разумный дефолт
   (`-fa on --fit on`, KV `q4_0`, спекуляция если есть).
3. Запустить: `python bench/bench.py suite.json` → `runs/results.jsonl`, логи серверов, ответы.
4. Зафиксировать базу: загрузка, VRAM, PP (короткий и ~12k), TG (лёгкий текст + 3 реальные задачи).

### Фаза 2. Тюнинг (по приоритету прироста)

Бюджет: 1 baseline + 4–6 тестов на модель, быстрые запросы (см. «Быстрый режим» в
`references/methodology.md`) — серия на модель ~10–15 минут.

1. **Спекулятивное декодирование** — обычно самый большой выигрыш:
   `draft-mtp` (если голова MTP в модели), `draft-simple` (маленькая draft-модель), `ngram-*` (повторяющийся текст).
   Менять `--spec-draft-n-max` (2–6) и `--spec-draft-p-min` (0.0–0.7); оптимум — по TG на реальных задачах,
   а не по «красивому» проценту принятия. Для повторяющегося контента пробовать `draft-mtp,ngram-simple`.
2. **KV-кэш**: `-ctk/-ctv` q4_0 ↔ q8_0 ↔ f16: сколько VRAM остаётся и не падает ли TG. С квантованным V
   обязателен `-fa on` (иначе сервер не стартует).
3. **Контекст**: максимальный, что влезает с запасом ≥1.5–2 ГБ; проверять скорость на глубине (32k/60k),
   а не только «влезло». Слишком большой контекст может резко замедлить спекуляцию.
4. **Размещение/загрузка**: `-ngl auto` + `--fit on` (дефолты) против ручного; `--no-mmap`/`--load-mode none`
   против mmap (важно только время загрузки).
5. **Батчи/потоки**: `-b/-ub` и `-t/-tb` — трогать последними; на GPU-инференсе почти не влияют,
   а `-ub` сверх дефолта ест VRAM.
6. **Задачи/профили**: длинный контекст и агентный режим могут требовать ДРУГИХ параметров спекуляции,
   чем обычный чат (проверять отдельными сериями).

### Фаза 3. Мультитёрн и качество

1. Кэш промпта: клиент должен слать `cache_prompt: true`; замер — `scripts/` сценарий
   (см. `references/methodology.md`, раздел «Кэш промпта»). Повтор запроса с общим префиксом должен
   пересчитывать единицы токенов, а не весь промпт.
2. Мышление/шаблон: проверить, какие режимы поддерживает шаблон модели (например только
   `xhigh|medium|low`), что «мысли» уходят в `reasoning_content`, а ответ — в `content`.
3. Реальные задачи (код/математика/инструкции): проверить, что ответы корректны во всех отобранных режимах.

### Фаза 4. Финализация

1. Выбрать основной профиль (максимум TG/стабильности) и 1–2 альтернативы (длинный контекст, агентный).
2. Собрать `launch/*.bat` из `assets/launch-template.bat` (или аналог для не-Windows).
3. Документы: `FINDINGS.md` (все замеры и обоснования), `LAUNCH.md` (как запускать + чего избегать),
   сводка `runs/summary.md` (генерирует `python bench/report.py`).
4. Честно перечислить ограничения: потолок железа, отсутствие фич в старом билде, несертифицированные
   компоненты (например чужой mmproj) и что осталось непроверенным.

## Что почти всегда НЕ помогает (проверено)

- Увеличение `-b/-ub`, `-t/-tb` на GPU — в пределах шума, `-ub 2048` только ест VRAM.
- Гонка за высоким процентом принятия спекуляции (`p-min` 0.8–0.9) — итоговый TG падает.
- Контекст «на всю память без запаса» — рост глубины режет скорость.
- `-fa off` с квантованным V-кэшем — сервер не стартует.
- Подключение чужого vision-проектора без подтверждения авторов модели.

## Разбор результата

Обязательные метрики каждого теста: время загрузки, VRAM, PP на 1.5k и ~12k, TG на лёгком тексте и на
2–3 реальных чатах, принятие draft и **средний TG на реальных задачах** — он и есть критерий выбора.
Разброс одного конфига ±5 % — это шум; отличающиеся меньше — считать равными и выбирать по простоте/запасу VRAM.

## Файлы скила

- `scripts/bench.py` — харнесс: поднимает `llama-server`, гоняет запросы, пишет `results.jsonl` + логи.
- `scripts/report.py` — сводная таблица в markdown.
- `scripts/probe_env.py` — снимок железа/рантайма (без изменений в системе).
- `references/methodology.md` — полная методика, дизайн экспериментов, метрики, шаблоны отчётов.
- `references/llama-cpp-playbook.md` — флаги, лог-сигналы, анти-паттерны.
- `assets/` — шаблоны suite/launch/документов.
